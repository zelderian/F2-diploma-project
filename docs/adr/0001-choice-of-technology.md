# ADR-001: Модель розміщення авторитетного ігрового сервера

**Статус:** Approved
**Дата:** 2026-11-11
**Автор:** Ошурко Б. С.
**Пов'язані вимоги:** [SRS-FUN-02](../srs.md#srs-fun-02), [SRS-FUN-03](../srs.md#srs-fun-03), [SRS-FUN-04](../srs.md#srs-fun-04), [SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01), [SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02), [SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01), [SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01), [SRS-NFR-OPS-01](../srs.md#srs-nfr-ops-01)

## Context (Контекст)

Специфікація вимог встановлює, що авторитет над станом матчу (рух, стрільба, шкода) має належати серверу, а не машині гравця ([SRS-FUN-02](../srs.md#srs-fun-02), [SRS-FUN-03](../srs.md#srs-fun-03)), частота оновлення має становити не менше 30 Гц ([SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01)), p95 RTT – не більше 100 мс ([SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02)), а метрики сервера мають бути доступні для Prometheus ([SRS-NFR-OPS-01](../srs.md#srs-nfr-ops-01)). Цільове навантаження під час апробації становить до 4 одночасних сесій по 3 гравці. Обмеженнями проєкту є бюджет хмарних витрат у межах кредитів AWS Educate / Free Tier (до 50 USD на місяць) та виконання робіт одним розробником.

Необхідно обрати модель розміщення процесу Unreal Engine, що виконує авторитетну симуляцію.

## Alternatives (Альтернативи)

**A1. Listen Server.** Сервер виконується в процесі гравця-хоста. Інфраструктурні витрати відсутні. Хост має повний доступ до пам'яті процесу та авторитетного стану, що унеможливлює виконання SRS-FUN-02 і SRS-FUN-03. Симуляція ворогів та реплікація розділяють CPU з рендерингом, що не гарантує 30 Гц. RTT інших гравців визначається висхідним каналом і типом NAT хоста. Вихід хоста завершує сесію (рушій не має вбудованої міграції хоста).

**A2. Dedicated Server на керованій платформі (Amazon GameLift).** Платформа керує флотом інстансів, розміщенням сесій (FleetIQ, Queues) та автомасштабуванням. Інтеграція потребує GameLift Server SDK (C++), окремого бекенд-компонента для запиту розміщення сесії та збирання серверних бінарних файлів у формат завантаження GameLift. Мінімальна вартість визначається погодинною оплатою інстансів флоту, що працюють постійно для підтримки резерву; конфігурація флоту, черг та ролей IAM збільшує обсяг інфраструктурного коду. Метрики сервера доступні передусім через Amazon CloudWatch, експорт у Prometheus потребує додаткового агента. Виникає залежність від API постачальника (Vendor Lock-in) для керування сесіями.

**A3. Dedicated Server у Docker-контейнерах на AWS EC2 (Docker Compose).** Серверні бінарні файли Linux пакуються в Docker-образ у GitHub Actions та розгортаються на інстансі EC2. Кілька контейнерів Dedicated Server виконуються на одному інстансі з різними UDP-портами. Перезапуск при збоях виконується політикою restart та перевіркою /healthz. Метрики експортуються напряму в Prometheus. Автомасштабування, розміщення сесій за регіонами та керування флотом відсутні й мають бути реалізовані самостійно за потреби.

Розглядався також варіант оркестрації Kubernetes з Agones; його відхилено на ранньому етапі, оскільки експлуатація кластера (керований EKS – близько 73 USD на місяць лише за площину керування) перевищує бюджет і надлишкова для 4 сесій.

## Decision (Рішення)

Обрано **A3: Dedicated Server у Docker-контейнерах на AWS EC2 з Docker Compose**.

Обґрунтування за метриками:

- **Авторитетність і безпека.** На відміну від A1, процес сервера ізольований від гравців; валідація RPC та Rate Limiting ([SRS-FUN-04](../srs.md#srs-fun-04)) виконуються в середовищі, недоступному клієнту.
- **Продуктивність.** Процес без рендерингу з обмеженням CPU контейнера (cpus: 0.5) забезпечує ≥ 30 Гц; розміщення в eu-central-1 відповідає цілі p95 RTT ≤ 100 мс для клієнтів у Центральній і Східній Європі. Відповідність перевіряється навантажувальною симуляцією ([SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01)).
- **FinOps.** Один інстанс c6i.large (близько 0,1 USD/год в eu-central-1) обслуговує 4 сесії; інстанс запускається лише на час тестування та апробації, що утримує витрати в межах бюджету. A2 потребує постійно активного флоту та додаткових компонентів.
- **Спостережуваність.** Прямий експорт /metrics у Prometheus виконує [SRS-NFR-OPS-01](../srs.md#srs-nfr-ops-01) без проміжних агентів.
- **Відтворюваність.** Той самий Docker-образ запускається локально, у CI та на EC2, що усуває розбіжність середовищ.

## Consequences (Наслідки)

**Позитивні:**

- авторитет над станом гри та захист від маніпуляцій клієнта;
- переносимість образу між локальним середовищем, CI та будь-яким хостом з Docker (відсутність Vendor Lock-in на рівні оркестрації);
- повний контроль над метриками, логами та конфігурацією мережі;
- прогнозована вартість за моделлю «оплата за години роботи інстансу».

**Негативні та ризики:**

- **Відсутність автомасштабування:** кількість сесій обмежена ресурсами одного інстансу; при зростанні навантаження потрібна міграція на A2 або Agones. Ризик знижується тим, що образ контейнера сумісний з обома варіантами.
- **Єдина точка відмови:** збій інстансу EC2 завершує всі активні сесії; Health Checks відновлюють лише процес, а не вузол ([SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01)). Прийнято як допустимий ризик для навчального проєкту.
- **Ручне розміщення сесій:** алгоритм призначення вільного контейнера (порту) лобі реалізується самостійно, що додає код та сценарії тестування.
- **Ускладнення CI/CD:** збирання Unreal Engine з вихідного коду потребує self-hosted runner або кешу збірки (диск ≥ 200 ГБ, RAM ≥ 16 ГБ); тривалість конвеєра без кешу перевищує 1 год ([SRS-NFR-INF-01](../srs.md#srs-nfr-inf-01)).
- **Операційна відповідальність:** оновлення ОС, ротація секретів, налаштування Security Groups (відкриття UDP-діапазону 7777–7780) виконуються розробником; помилка конфігурації створює ризик безпеки.
- **Вартість трафіку:** вихідний трафік AWS тарифікується окремо; реплікація 3 гравців генерує орієнтовно 30–60 Кбіт/с на клієнта, що необхідно контролювати метриками.
