# 1 АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ІСНУЮЧИХ АНАЛОГІВ

## 1.1 Критерії відбору аналогів

Як аналоги обрано програмні продукти, що вирішують суміжну задачу забезпечення мережевої та бекенд-інфраструктури багатокористувацьких ігор: Photon, Nakama, PlayFab. Порівняння виконано за технічними критеріями: тип архітектури, протоколи обміну, система керування базами даних, модель авторитетності стану, відмовостійкість, хмарна інфраструктура.

## 1.2 Аналіз існуючих аналогів

### 1.2.1 Photon (Exit Games)

Photon реалізує хмарну кімнатну (room-based) архітектуру з розподілом ролей між Name Server, Master Server та Game Server. Розгортання можливе як керований сервіс (Photon Cloud) або на власних вузлах (Photon Server). У режимах Host та Shared авторитет над станом гри делегується клієнту, у режимі Server (Photon Fusion) використовується виділений авторитетний сервер. Масштабування є горизонтальним за рахунок незалежних кімнат; стан кімнати локалізовано на одному вузлі.

Обмін даними виконується власним прикладним протоколом поверх UDP з рівнем надійної доставки; також підтримуються TCP та WebSocket. Інтеграція із зовнішнім бекендом реалізується через HTTP Webhooks. Стан кімнати зберігається в оперативній пам'яті Game Server та не персистується; консистентність у Photon Fusion забезпечується tick-орієнтованою симуляцією з клієнтським прогнозуванням (Client-Side Prediction) та повторною симуляцією (Resimulation).

Технічними обмеженнями є пропрієтарний протокол із закритим ядром (Vendor Lock-in), орієнтація основних SDK на Unity без нативної інтеграції із системою Replication рушія Unreal Engine, обмежений захист від Cheating у режимах Host та Shared, а також ліцензування за кількістю одночасних підключень (CCU).

### 1.2.2 Nakama (Heroic Labs)

Nakama є модульним монолітом: єдиним серверним процесом на Go з розширюваним runtime (Go, Lua, TypeScript/JavaScript). Серверно-авторитетні матчі виконуються як обробники (Match Handlers) із фіксованою частотою оновлення (Tick Rate) усередині процесу. За документацією виробника, кластерний режим для горизонтального масштабування доступний у комерційних редакціях.

Клієнтський API реалізовано через gRPC та REST (HTTP); взаємодія в реальному часі виконується через WebSocket із серіалізацією Protocol Buffers та JSON. Як сховище даних використовується PostgreSQL або CockroachDB; консистентність облікових записів, колекцій даних, таблиць лідерів та віртуальних гаманців забезпечується ACID-транзакціями СУБД, тоді як стан активного матчу зберігається в пам'яті процесу.

До технічних обмежень належать виконання лише скриптової логіки в Match Handler без заміни повноцінної симуляції рушія (для Unreal Engine потрібен окремий Dedicated Server), центральна роль реляційної СУБД як точки запису, що обмежує пропускну здатність, та накладні витрати інтерпретованого runtime для логіки з високою частотою тиків.

### 1.2.3 PlayFab (Microsoft Azure)

PlayFab є керованою хмарною платформою (SaaS) із сервіс-орієнтованою архітектурою на базі Azure: окремі сервіси автентифікації, економіки, таблиць лідерів та Multiplayer Servers. Multiplayer Servers запускає ігрові сервери у контейнерах на віртуальних машинах Azure; виділення сервера виконується за запитом із пулу резервних (Standby) серверів. Інтеграція здійснюється через Game Server SDK (GSDK), що має підтримку Unreal Engine.

Клієнтський API реалізовано як REST поверх HTTPS із форматом JSON та автентифікацією на основі сесійних токенів (SessionTicket, EntityToken). Внутрішні сховища не розкриваються; доступ до даних здійснюється через моделі Title Data, Player Data та Entity Objects, а для запобігання конфліктам одночасного запису передбачено механізми версіонування об'єктів.

Технічними обмеженнями є залежність від екосистеми Microsoft Azure (Vendor Lock-in), ліміти частоти викликів API (Rate Limits), додаткова затримка запуску сервера при вичерпанні пулу Standby, зростання вартості обчислень пропорційно кількості активних сесій та обмежена спостережуваність (Observability) через закритість внутрішньої інфраструктури.

### 1.2.5 Аналітичний висновок

Аналіз Photon, Nakama та PlayFab виявив низку архітектурних обмежень, що ускладнюють їх застосування для кооперативної гри на Unreal Engine 5. Photon використовує пропрієтарний протокол і орієнтований на Unity, а режими Host та Shared делегують авторитет над станом клієнту, що знижує захищеність від Cheating. Nakama реалізує серверно-авторитетні матчі як скриптову логіку всередині монолітного процесу, що не замінює повноцінну симуляцію рушія і робить реляційну СУБД центральною точкою запису. PlayFab є закритою керованою платформою: ліміти частоти викликів API, залежність від Azure та обмежена спостережуваність створюють ризики Vendor Lock-in і непередбачуваної вартості під навантаженням.

Обраний у проєкті стек вирішує зазначені проблеми. Використання Authoritative Dedicated Server на базі нативної системи Replication рушія Unreal Engine 5 зберігає авторитет над станом на стороні сервера та виключає довіру до клієнта, а серверна валідація RPC і обмеження частоти запитів (Rate Limiting) знижують ризик маніпуляцій. Контейнеризація в Docker та автоматизований конвеєр CI/CD (GitHub Actions, SonarQube, Trivy) забезпечують відтворюваність збірок і контроль якості коду, а експорт метрик у Prometheus і візуалізація в Grafana усувають обмеження спостережуваності, характерні для закритих платформ. Окремий сервіс прогресії на Go з PostgreSQL та Redis відокремлює персистентні дані від ігрової симуляції, що дозволяє масштабувати їх незалежно.

Архітектурним компромісом (trade-off) є відмова від готових керованих сервісів на користь власної експлуатації інфраструктури: зростають трудомісткість розробки та відповідальність за відмовостійкість. Цей компроміс обґрунтований вимогами до контролю над станом гри, прозорості метрик і відсутності залежності від постачальника. Подальше проєктування архітектури, включаючи схеми взаємодії компонентів, модель C4 та рішення щодо відмовостійкості, наведено у Розділі 2.
